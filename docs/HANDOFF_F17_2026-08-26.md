## 8. Current definitions (verbatim semantics; source of truth in code/ADR)

Sources: `src/gnosis/kernel/evidence_capture.py` (`verify_bundle` at
~line 1203, `write_bundle_manifest` at ~line 1159,
`_is_git_machinery_tamper` at ~line 167, exit codes at ~line 144),
`src/gnosis/kernel/git_evidence.py` (`git_topology_eligible` at ~line 56),
and ADR-0027 "BLOCKER 2" section. The ladder:

- **SELF-CONSISTENCY (integrity)** — the bundle agrees with its own
  manifest. Provided by `verify_bundle(bundle)` with no anchor: recomputes
  the SHA-256 of every file and the `bundle_digest`
  (= `hash_canonical` over the sorted files map); fails closed on a
  missing/unparseable manifest, a file present-but-unlisted,
  listed-but-absent, or hashed differently, or a digest mismatch. Catches
  drift, corruption, and any edit that does NOT recompute the manifest.
  The manifest cannot hash itself and names itself the one unlisted file.
- **TAMPER-EVIDENCE** — an edit is detectable against a root of trust held
  OUTSIDE the bundle. Provided by
  `verify_bundle(bundle, expected_digest=…)` where `expected_digest` is a
  `bundle_digest` recorded elsewhere. This defeats the
  recomputed-manifest attack (an editor who rewrites a file AND recomputes
  the manifest presents a self-consistent bundle; the external anchor
  still refuses it).
- **AUTHENTICITY (trusted provenance)** — unforgeable proof of WHO
  produced the bundle. Requires a cryptographic signature over
  `bundle_digest` with a managed key. **Out of scope for this phase —
  declared, not faked.** Nothing in the repo claims "cryptographically
  tamper-proof".
- **`expected_digest`** — the externally recorded `bundle_digest` a
  verifier passes into `verify_bundle`. Today it lives in two anchors that
  already existed (nothing new was invented): (1) the git commit carrying
  the bundle (content-addressed blobs, hash-chained DAG), and (2) the
  digest value written into ADR-0027's Evidence sections, a separate
  committed file. Residual: only as strong as the immutability of that
  committed record — see BLOCKER C.
- **`git_topology_eligible(repo) -> (bool, reason)`** — resolves the git
  topology via `git rev-parse`, treating a `.git` redirect file as
  adversarial input (resolved paths are checked to lie inside the
  canonical tree, never followed blindly). Eligible only when `.git` is a
  directory AND git-dir == common-dir == `repo/.git`. `run_capture` calls
  it before anything runs; an ineligible topology (linked worktree,
  submodule working dir, separate-git-dir clone, `.git` file pointing
  outside) yields **`MACHINERY_UNOBSERVABLE`, exit 10**, runs no checks,
  and is never CLEAN. A non-repo directory is eligible (no machinery to
  tamper). Rationale: in a linked worktree HEAD/index live in the external
  per-worktree git-dir and **config/hooks/refs live in the external
  common-dir**, so a hook install during capture was invisible —
  reproduced OS-real returning CLEAN before the fix.

Related exit vocabulary (full set in `evidence_capture.py`): 0 clean /
1 checks failed / 2 TREE_MUTATED / 3 IDENTITY_UNAVAILABLE /
4 INPUTS_MUTATED / 5 UNOBSERVED / 6 UNPROTECTED / 7 PREPARATION_DRIFT /
8 STREAMS_MUTATED / 9 MACHINERY_MUTATED / 10 MACHINERY_UNOBSERVABLE.

## 9. BLOCKERS for the third review (operator-dictated scope)

### BLOCKER A — Git machinery classification

Audit, surface by surface, the classification of git machinery. Minimum
list:

- `HEAD`
- `index`
- `sharedindex.*`
- `refs/**`
- `packed-refs`
- `refs/replace/**`
- `objects/info/alternates`
- `objects/info/http-alternates`
- `info/grafts`
- `shallow`
- `config`
- `config.worktree`
- `commondir`
- `hooks`
- any other relevant git surface.

**Explicit constraint: `packed-refs` may NOT keep its current "inert
bookkeeping" classification without a demonstration.** (ADR-0027's audit
currently argues it safe by prose; that argument is exactly what this
blocker challenges.)

Each surface must be investigated SEMANTICALLY for whether it can alter:

- commit resolution
- tree resolution
- object resolution
- ancestry
- Git execution
- repository identity
- trust boundary

Note the standing shape of the current defence, to be tested rather than
assumed: hooks/config are judged (`MACHINERY_MUTATED`); HEAD/index/refs
changes are claimed to be caught by the content-fingerprint binding
(`TREE_MUTATED`, measured for `git checkout` in the interval); everything
else is counted. Surfaces like `refs/replace/**`, `objects/info/alternates`,
`info/grafts`, `shallow`, `config.worktree` were NOT individually
demonstrated in review 2 — they are this blocker's core.

### BLOCKER B — Gnosis-managed worktrees

Current state: linked worktrees fail closed (`MACHINERY_UNOBSERVABLE`).
That is SAFE — but GNOSIS itself uses worktrees as part of its execution
architecture (ADR-0007 provenance-gated worktrees, ADR-0009 governed
isolation), so a capture can never run inside the very workspaces Gnosis
creates.

The next session must determine whether F-17 needs to work inside real
Gnosis worktrees. If YES: design specific support for **GNOSIS-MANAGED
WORKTREES** without ever admitting an arbitrary external gitdir. Required
distinction:

- worktree known to and created by Gnosis (provenance-gated) — candidate
  for support;
- arbitrary external gitdir/common-dir — stays refused;
- unknown topology — stays fail-closed.

Unknown topologies must NEVER degrade to a protected-looking capture.

### BLOCKER C — Trust anchor

`verify_bundle(bundle, expected_digest=…)` is accepted. What is NOT
settled is **where `expected_digest` really lives**. Today it lives in
ADR-0027 (a committed file) — which is inside the surface a worker with
write access to the repo can modify.

The next session must search for whether Gnosis already possesses a
store/ledger **controlled by the Director and outside the
worker-modifiable surface** (candidates to examine: `kernel/ledger.py`'s
hash-chained `RunLedger`, the claims plane, `.gnosis/state/`) and, if one
fits, anchor `expected_digest` there.

Keep the three levels SEPARATE at all times: SELF-CONSISTENCY /
TAMPER-EVIDENCE / AUTHENTICITY. Do NOT introduce Cosign, in-toto, TUF,
PKI or key management unless it becomes unavoidable. Cryptographic
AUTHENTICITY may remain a later phase.
