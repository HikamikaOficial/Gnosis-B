5. THE MINIMAL SOLUTION — three candidates, none implementable under this
--------------------------------------------------------------------------------------
   stage's authorization

  (A) MOVE THE PAYLOAD TO STDIN
      Evidence FOR: the installed CLI is claude 2.1.247; `claude --help` gives
      `Usage: claude [options] [command] [prompt]`, documents `-p/--print` as
      "Print response and exit (useful for pipes)", and documents
      `--input-format <format>  Input format (only works with --print): "text"
      (default), or "stream-json"`. A text input channel in print mode is
      therefore a documented feature.
      WHY NOT NOW: proving the EXACT semantic equivalence needs a real turn,
      which is a PROVIDER CALL — explicitly out of scope for this stage. And it
      changes the Claude invocation contract: `ExecutionResult.command` records
      argv as provenance and the replay/cassette system keys on it, so moving
      the prompt out of argv changes recorded provenance and every argv-asserting
      test. The review says "NO cambies semántica de Claude por conveniencia."
      COST: a semantic change to the runner + a provider-call validation.

  (B) TRUSTED SHORT BOOTSTRAP, PAYLOAD ON A SEPARATE CHANNEL   <-- RECOMMENDED
      CreateProcessWithLogonW launches a SHORT (<1024) trusted bootstrap under
      the Worker SID; the bootstrap reads the exact argv from a file the Director
      wrote before the launch and CreateProcess-es the real CLI **as itself** —
      already the Worker SID, so the ordinary 32767-character limit applies and
      NO additional privilege is needed.
      WHY IT IS THE MINIMAL ONE: it changes NEITHER Claude's semantics (the argv
      is reconstructed byte-for-byte) NOR the privilege set (still
      CreateProcessWithLogonW, still no SeImpersonatePrivilege).
      COST, STATED: a new trusted component enters the TCB, and the argv payload
      file becomes LOAD-BEARING FOR INTEGRITY — anything that could rewrite it
      between write and exec would control the Worker's own argv. Its ACL and
      its position relative to the worktree need a design decision, which is
      exactly the kind of decision this stage may not take alone.

  (C) A DIFFERENT WINDOWS PRIMITIVE
      Measured on this machine (see the caller-context audit):
        CreateProcessWithLogonW  reachable  cap  1024   DISQUALIFIED by payload
        CreateProcessWithTokenW  reachable  cap 32767   needs SeImpersonate
        CreateProcessAsUserW     NOT reach. cap 32767   needs SeAssignPrimaryToken
      The Director holds SeImpersonatePrivilege ENABLED, so LogonUserW +
      CreateProcessWithTokenW WOULD fit the payload.
      WHY NOT NOW: reachability is not authorization. This makes the trusted
      launcher DEPEND on SeImpersonatePrivilege, a privilege the review itself
      enumerates as dangerous and which was never approved as a launcher
      dependency; it also forecloses the "broker/service" option that
      docs/F17_DEDICATED_WORKER_PROBE_PLAN.md §4 marks as PREFERRED for
      production. The review is explicit: "No cambies silenciosamente a una API
      con privilegios mayores", and STOP if "only solution requires dangerous
      trusted privileges not previously approved".

  No candidate is clean AND within this stage's authority. Hence the named STOP.

   the gate, and all three are Stage-5 requirements that are UNMET today)

      name — including CLAUDE_CODE_MESSAGING_TOKEN, CLAUDE_CODE_MESSAGING_SOCKET

      There is no allowlist anywhere. The required "Director sentinel ABSENT from
      the Worker environment" property is not achievable without building one.

  H1  STDIN. The runner never sets `stdin=`, so the child inherits the
      Director's stdin handle. Live probe: the child sees fd 0, isatty=True.
      No designed read-only endpoint exists.

  D1  DESCENDANT CONTAINMENT. No Windows Job Object anywhere in src/. Timeout and
      cancellation call terminate() then kill() on the DIRECT CHILD ONLY.
      PROVEN BY LIVE PROBE: a grandchild spawned by the child kept running after
      the run was cancelled (marker advanced '9' -> '16' after cancellation
      returned). A Worker's descendants outlive the run today.
      WORKER DESCENDANT CONTAINMENT GAP — recorded, not designed around.

      Probe honesty note: the FIRST version of this probe reported "contained".
      It was wrong — `open(p,'w').write(i) or time.sleep(...)` short-circuits,
      because `write` returns a truthy character count, so the grandchild
      finished instantly and the probe measured its own bug. Corrected, re-run,
      and recorded rather than quietly fixed: it is L-0061 arriving from the
      probe side within a day of being written.
