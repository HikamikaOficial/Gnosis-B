1. B ARCHITECTURE, FINAL
--------------------------------------------------------------------------------------
    Director (trusted, High, elevated)
      | seals a LaunchSpec into the trusted launch root
      | CreateProcessWithLogonW(LOGON_WITH_PROFILE, CREATE_SUSPENDED)
      |   lpApplicationName = the absolute trusted runtime
      |   lpCommandLine     = "<runtime>" -I "<bootstrap.py>" "<spec.json>" <digest>
      |                       264 characters measured, budget 512, OS cap 1024
      |   lpEnvironment     = the WORKER's profile block + a named allowlist
      |   lpCurrentDirectory= the run's authorized workspace
      |   NO std handles are passed at all
      v
    Bootstrap (runs AS THE WORKER, bytes are Worker-RX / WRITE-DENIED)
      | reads the sealed spec, recomputes launch_spec_digest, refuses on mismatch
      | re-validates the executable and the cwd
      | opens stdout/stderr ITSELF; stdin = DEVNULL
      | CreateProcess (ordinary, ~32767 limit) with the EXACT logical argv
      v
    Claude CLI — the logical command, unchanged in every byte

    PROPERTY PROVEN: logical argv before == logical argv after.

WHY NO HANDLE CROSSES. `CreateProcessWithLogonW` creates the process through the
Secondary Logon service, in a different logon session, and handle inheritance
across that is not something to assume. Naming the output PATHS in the sealed
spec lets the bootstrap open them itself, as the Worker, with the Worker's own
rights — so the handle-leak question has a STRUCTURAL answer ("there is nothing
to leak") rather than an audited one.


2. LAUNCHSPEC SCHEMA
--------------------------------------------------------------------------------------
    gnosis.trust.launch_spec.v1
    { schema, launch_id, executable, argv[], cwd, stdout_path, stderr_path, run_id }

    launch_id     ^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$, no "..", becomes the filename
    executable    absolute, drive-qualified. UNC REFUSED (it resolves through the
                  network redirector, so what it names is decided off this machine)
    argv          non-empty tuple of str; a NUL is REFUSED, because a NUL
                  terminates a Windows command line and the OS would silently
                  truncate the argument — the one thing this stage may not do
    cwd/out/err   absolute, drive-qualified
    NO SECRETS.   No credential, no token, no environment block. The environment
                  is built by the launcher directly into the process and never
                  travels through a file the Worker can read.

    logical_command_digest is a DERIVED property over argv alone, never stored:
    storing it beside argv would put one fact in two places with no way for them
    to disagree, which is Stage 3's RM13 defect. It is what provenance and replay
    bind to, because it is unchanged by which transport carried the command.


3. CANONICALIZATION AND DIGEST
--------------------------------------------------------------------------------------
    canonical bytes  canonical_json_bytes(to_dict())   — ADR-0004, the ONE primitive
    launch_spec_digest = hash_canonical(to_dict())     — no second hashing impl
    bounded          MAX_LAUNCH_SPEC_BYTES = 1_048_576, checked against what was
                     ACTUALLY READ, not a prior stat() — a file whose size changes
                     between the two is precisely the case not to relax for
    refused          unknown field, missing field, unknown schema, non-object,
                     bad UTF-8, non-JSON, and a payload that is not in CANONICAL
                     FORM even when its digest matches (something re-serialised it
                     after it was sealed; that is not a launch we were told to run)

5. PAYLOAD INTEGRITY PROTOCOL
--------------------------------------------------------------------------------------
    1 build the LaunchSpec from the Director's own values
    2 canonicalize
    3 atomic_write_bytes into the trusted launch root (temp -> fsync -> replace)
    4 RE-READ the bytes from disk
    5 derive launch_spec_digest FROM WHAT IS ON DISK, never from the object
    6 only then create the bootstrap, carrying that digest on the command line

    The digest travels on the COMMAND LINE, not inside the file. A value stored
    beside the thing it protects proves self-consistency and nothing else
    (L-0059); here the anchor is external to the payload by construction.


6. BOOTSTRAP ARCHITECTURE AND ITS THREAT MODEL
--------------------------------------------------------------------------------------
THE BOOTSTRAP RUNS UNDER THE WORKER SID. It is therefore NOT treated as trusted
merely because its binary is protected. It is written so that subverting it buys
an attacker nothing it did not already have:

    * it holds NO credential and never sees one
    * it receives NO privileged handle
    * it makes NO security decision — it only refuses an instruction that fails
      its seal
    * the process it creates runs as the SAME SID it already runs as, so it can
      grant no authority it does not already possess

A Worker that subverted it could run whatever it likes AS THE WORKER, which it
could do anyway. What it must not be able to do is make the Director's launch
execute a DIFFERENT logical command — and that is what the digest prevents.

FORBIDDEN AND TESTED: no shell, no `cmd /c`, no `powershell -Command`, no PATH
search (`executable=` is always the sealed absolute image), no eval/exec, no
dynamic import, no environment-derived configuration. Invoked with `-I`, so
PYTHONPATH, the user site directory and every Python environment variable are
ignored: a Worker cannot inject a module by setting a variable. Its package root
is derived from its OWN file location inside the Worker-RX tool root.

WORKER-SID BOOTSTRAP THREAT, QUALIFIED. The bootstrap's bytes and its runtime are
Worker-RX and WRITE-DENIED (probe T9: writing the runtime and the bootstrap both
return PermissionError), so a Worker cannot rewrite the code that is about to
validate its launch. Concurrent tampering by a PREVIOUS worker process is
addressed by the job lifecycle in §13: no worker process survives a run.

10-12. CREATION SEQUENCE, CREATE_SUSPENDED VERIFICATION, JOB CONFIG
--------------------------------------------------------------------------------------
    1  CreateProcessWithLogonW(..., CREATE_SUSPENDED | CREATE_UNICODE_ENVIRONMENT
                                    | CREATE_NO_WINDOW)
    2  OpenProcessToken(child)
    3  read TokenUser SID, integrity, groups, privileges
    4  verify_worker_token(...)  -> SID, integrity, non-admin, no dangerous privilege
    5  CreateJobObject
    6  SetInformationJobObject(ExtendedLimitInformation,
                               LimitFlags = JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE)
       BREAKAWAY_OK and SILENT_BREAKAWAY_OK are NOT set
    7  AssignProcessToJobObject
    8  IsProcessInJob must be TRUE
    9  ResumeThread — and only here

    Any failure: never resume, TerminateProcess, close every handle, raise.
    UNVERIFIED WORKER CODE NEVER BEGINS EXECUTION.

    The VERDICT (step 4) was extracted into `verify_worker_token`, a pure
    function, precisely so each refusal is a unit test rather than something only
    a real account could reach. The ORDER is pinned by AST assertions; the
    OBSERVED values are proved by the OS-real probe. Both are reported for what
    they are.

17-18. STDOUT/STDERR MODEL AND HANDLE AUDIT
--------------------------------------------------------------------------------------
    stdout/stderr are the exact files the sealed spec names, opened by the
    bootstrap in the same truncating binary mode the previous runner used, so
    capture, stderr separation, exit-code propagation, timeout and cancellation
    semantics are unchanged. Exit-code propagation is tested (a command exiting 7

    HANDLE AUDIT: NO handle is passed across the identity boundary at all.
    STARTF_USESTDHANDLES is never set; startup.dwFlags, hStdInput, hStdOutput and

25-26. RUNNER INTEGRATION AND THE SAME-USER-FALLBACK DEFENSE
--------------------------------------------------------------------------------------
    `CLIRunner.run(..., launcher=..., require_trusted_launch=...)` is the single
    decision point. `WorkerLauncher` is a Protocol; `TrustedWindowsWorkerLauncher`
    is production; a test fake is explicit and is REFUSED when the trusted launch
    is required.

    THERE IS NO try/except AROUND THE LAUNCH. A failure propagates and the run
    fails. Tested: `require_trusted_launch=True` with no launcher raises AND the
    command does not run at all (a file the command would have created is absent).
    Mutants WM1, WM2 and WM3 all die.

    PROVENANCE KEPT SEPARATE: `ExecutionResult.command` keeps its historical
    meaning — the LOGICAL command — so replay and cassettes are untouched. The
    transport is recorded in a NEW `ExecutionResult.launch` field: launcher
    kind/version, launch_spec_digest, logical_command_digest, observed worker SID,
    integrity, containment and the transport length. The bootstrap's argv is never
    merged into `command`.

40. RESIDUAL RISKS
--------------------------------------------------------------------------------------
    S1  The launch root, the tool root and the DPAPI blob depend on ACLs that
        Stage 8 provisioning must establish in production. The probe applied them
        to probe paths only; nothing production-side is provisioned yet.
    S2  TOOLCHAIN RELOCATION IS REQUIRED. `claude.exe` currently lives in the
        Director's profile and is unreachable by a dedicated worker. Until it is
        relocated into a worker-RX root, the production path cannot run.
    S3  The Python runtime (62 MB, 3434 files) is inside the TCB, because the
        bootstrap executes on it and a Worker-writable runtime would defeat the
        seal. That is a large surface; a smaller native bootstrap was deliberately
        NOT written (the review said not to jump to one for aesthetics), and the
        size is reported so the trade is visible.
    S4  DPAPI machine binding is not launcher binding. Anything on this machine
        that can read the blob can unprotect it; the ACL is the boundary.
    S5  The Job Object contains descendants; it is not a security boundary against
        a Worker with other means. A Worker that could obtain a handle to a job
        outside its own could still act — nothing observed suggests it can, and it
        is listed rather than assumed away.
    S6  Stage 5 does not wire RunIdentity. Until Stage 6 does, the observed SID is
        produced but not yet bound to a run's trusted identity.
    S7  Single-worker lifecycle: the guarantee that no previous worker process
        survives rests on KILL_ON_JOB_CLOSE plus the probe's measured "0 worker
        processes alive". Multi-worker was NOT invented and is not supported.


41. DECISIONS REQUIRING INDEPENDENT REVIEW
--------------------------------------------------------------------------------------
    D1  The output PATHS travel in the sealed spec and the bootstrap opens the
        endpoints itself, so NO handle crosses the logon boundary. This is a
        deviation from a STARTF_USESTDHANDLES design and the reason is that
        inheritance across the Secondary Logon service is not something to assume.
    D2  `LogonUserW` + `LoadUserProfileW` are used ONLY to build the environment
        block. The token is never used to create a process — that would be
        `CreateProcessWithTokenW` and the `SeImpersonatePrivilege` dependency the
        review rejected. Confirm this narrow use is acceptable.
    D3  `LoadUserProfileW` requires the Director to hold SeBackup/SeRestore, which
        an elevated administrator does. This is a dependency on EXISTING Director
        privileges, not an acquisition of new ones — confirm.
    D4  The transport budget is 512 with a hard refusal, half the 1024 cap.
    D5  The token verdict was EXTRACTED into a pure function so its refusals are
        unit-testable. Confirm that the split does not weaken the OS-real proof.
    D6  Structural (AST) assertions pin the creation ORDER and the job FLAGS;
        the OS-real probe proves the observed behaviour. Confirm the division.
    D7  The runtime inside the TCB (62 MB) versus writing a small native
        bootstrap.
    D8  `ExecutionResult.launch` is a NEW field carrying transport provenance
        while `command` keeps the logical semantics. Confirm the replay/cassette
        contract is unaffected.
