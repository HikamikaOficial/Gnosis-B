2. RUNIDENTITY — FINAL SCHEMA  (gnosis.trust.run_identity.v1)
  schema, task_id, run_id, repository_id, head_sha, tree_identity, bundle_path,
  owner_worker_sid, deployment_digest, epoch

3. IMMUTABLE FIELDS vs MONOTONIC TRUSTED STATE
  IMMUTABLE (frozen dataclass, fixed at creation, never carried into an update)
    every field of RunIdentity above.
  MONOTONIC TRUSTED STATE (TrustedRunRecord, OUTSIDE the identity)
    publication_state, anchor_record_digest.
  transition() carries NO identity, so a lifecycle change has nothing to
  rewrite an immutable field with. Enforced three ways: the dataclass is
  frozen; the store's update API accepts no identity; and every update is a
  compare-and-set on expected_identity_digest, so a record whose identity was
  tampered with refuses the next transition.

4. PUBLICATION STATE MODEL — and why it is a NEW primitive
  RunState and TaskState were inspected FIRST and are NOT reused. The reason is
  not vocabulary, it is WHERE THEY LIVE: RunState is persisted in RunStore's
  meta.json, inside the run directory the worker owns and can write. A worker
  able to write SUCCEEDED there would be writing its own publication
  permission. The trusted gate must read state from a store the worker cannot
  write, so PublicationState is the minimum separate primitive and models ONLY
  "may this run's evidence be authoritatively published":
      NOT_PUBLISHABLE -> PUBLISHABLE -> ANCHORED
  It adds no RUNNING, no FAILED, no vocabulary another machine already owns.

5. TRANSITION RULES (monotonic; there is no edge back)
  NOT_PUBLISHABLE -> PUBLISHABLE      permitted
  PUBLISHABLE     -> ANCHORED         permitted, and only while naming the
                                      digest of a CONFIRMED AnchorRecord
  everything else                     FAIL CLOSED, including
    ANCHORED -> PUBLISHABLE, ANCHORED -> NOT_PUBLISHABLE, ANCHORED -> ANCHORED,
    PUBLISHABLE -> NOT_PUBLISHABLE, NOT_PUBLISHABLE -> ANCHORED (skipping),
    an unknown target, a missing record, a stale expected identity.
  ANCHORED is never marked before the publisher has produced AND re-read the
  record. The DURABLE ORDERING of that write against this mark (write-through
  watermark, crash recovery) is Stage 4 and is NOT simulated here.

6. OWNER_WORKER_SID CONTRACT (frozen)
  form       canonical Windows SID string, validated strictly against
             ^S-1-\d+(-\d+){1,15}$. A username, a display name, an environment
             variable or any caller-chosen label is REFUSED.
  provenance TRUSTED LAUNCHER / DIRECTOR, never worker input. In Stage 5 it is
             the OS-observed TokenUser SID of the token the worker was actually
             launched with. Stage 3 validates the FORM and does not invent that
             token; fixtures use syntactically valid synthetic SIDs.
  The worker cannot modify RunIdentity: it is frozen, it lives in the trusted
  store, and Worker WRITE = denied is the ACL property Stage 6/8 provisioning
  must establish.

7. DEPLOYMENT_DIGEST BINDING
  Bound into RunIdentity and validated by FORM ONLY (present, non-empty,
  64-char lowercase hex). trust.anchor does NOT import trust.deployment, so the
  1052-line deployment module does not become a transitive publisher dependency
  to carry a digest the publisher merely compares. No caller-provided override
  exists: the value is fixed at identity creation and the gate compares it, it
  never accepts one.
  STATED PRECISELY: deployment_digest proves EXACT OBSERVED DEPLOYMENT IDENTITY.
  It does NOT by itself prove that the deployed bytes were built from the
  claimed Git commit — Stage 2's package_version/source_commit/source_tree are
  OBSERVED DEPLOYED PACKAGE CLAIMS. Binding and provenance are separate; the
  deployed-package to committed-source-tree check belongs to the final
  composition, and no build-provenance system was implemented here.

8. EPOCH / GENERATION — REUSED, NOT INVENTED
  claims.TaskClaim.epoch is already a monotonic per-task fencing generation
  that survives every status change (claims.py). RunIdentity records that
  value; the gate compares it against the trusted expectation. No
  publication_nonce, no second generation scheme.
  Property demonstrated: an artifact authorized for epoch E1 cannot be
  published as belonging to E2, in either direction.

9. RUN-ID UNIQUENESS MECHANISM
  EXISTING LOCUS: RunStore.create_run creates runs/<run_id>/ with
  mkdir(exist_ok=False) (run_store.py:77), so a duplicate id raises at
  creation; run_id itself (ids.py:18) is ms-timestamp + 4 random bytes.
  THE GAP IT LEAVES: delete the run directory and the id can be recreated.
  CLOSED IN THE TRUST PLANE: TrustedRunIdentityStore.create binds a run_id to
  its identity digest permanently. A second create with a DIFFERENT identity is
  REFUSED; an identical one is idempotent and does NOT reset state. So
  create -> delete -> recreate-with-different-identity fails closed, and old
  evidence cannot be presented as the new run's.
  Additionally: run_id becomes a filename, so anything that could climb out of
  it (.., separators, drive letters, reserved shapes) is refused BEFORE it is
  joined to a path.

10. STORE SEMANTICS
  one JSON file per run under the trusted root;
  atomic_io.atomic_write_text (write-tmp + os.replace) so no reader observes a
    torn record — REUSED, not re-implemented;
  file_lock.FileLock around every read-modify-write — REUSED, the kernel's
    established cross-process pattern — so two trusted writers cannot silently
    drop a transition and a monotonic state cannot regress by lost update;
  deterministic serialization (json sort_keys) and a canonical identity digest
    via hash_canonical (ADR-0004);
  fail closed on: missing file, unreadable file, malformed JSON, unknown
    schema, unknown publication state, unknown/extra fields, a record filed
    under a different run_id than it carries;
  no silent replacement of an existing identity, ever.
  ACLs are NOT implemented here; the model assumes Worker WRITE = denied, to be
  established by Stage 6/8 provisioning.

11. PUBLICATION AUTHORIZATION GATE
  authorize_publication(store, PublicationRequest) -> PublicationDecision
  A pure decision over trusted inputs: it reads the trusted store, compares it
  to the trusted request, performs NO bundle I/O, consults NO worker-supplied
  field and CHANGES NOTHING — so a refusal cannot leave half a state behind.
  Required, in this order (identity BEFORE state, so a mismatched request is
  never answered with a state-flavoured verdict like ALREADY_ANCHORED):
    1  run_id is a valid, storable id
    2  the record exists and is readable       (unknown/corrupt -> REFUSED)
    3  supported schema                        (enforced by read())
    4  the stored identity is for this run_id
    5  owner_worker_sid matches
    6  deployment_digest matches
    7  repository_id / head_sha / tree_identity match
    8  epoch matches
    9  the identity is not corrupted or superseded (CAS digest)
   10  state: ANCHORED -> ALREADY_ANCHORED (explicit idempotent path);
       PUBLISHABLE -> AUTHORIZED; anything else -> REFUSED
  The ONLY worker-influenced value in the whole flow is the bounded run_id that
  Stage 6 will carry over IPC, and by itself it authorizes nothing.

12. ANCHOR V2 SCHEMA  (gnosis.anchor.v2)
  v1 fields + deployment_digest + run_identity_digest.
  Two fields, each carrying a guarantee V1 could not:
    deployment_digest    WHICH trust plane produced this anchor
    run_identity_digest  WHICH exact authorized run it belongs to — the whole
                         immutable identity, owner SID and epoch included, in
                         one value
  owner_worker_sid and epoch are NOT repeated as separate fields: they are
  already bound unambiguously by run_identity_digest. Nothing was added merely
  because it exists.
  verify_anchored_bundle gained optional expected_deployment_digest /
  expected_run_identity_digest; supplying either asserts the F-17 binding.

13. V1 COMPATIBILITY BEHAVIOUR
  reader     recognises historical V1 records and verifies them under their
             historical contract (chain + authoritative bundle digest);
  writer     emits V2 ONLY (CURRENT_ANCHOR_SCHEMA);
  guarantee  a V1 record can NEVER satisfy a deployment-bound verification —
             it carries no binding, and it says so as its own type
             (AnchorNotDeploymentBound), not as a generic mismatch;
  no silent upgrade: a V1 record is never read as a V2 one with a defaulted
  digest, and to_dict emits the V2 keys ONLY for V2 so a historical V1 digest
  re-derives BYTE FOR BYTE and historical chains keep verifying.

14. SCHEMA-CONFUSION DEFENCES (the seven required cases)
  1 V2 missing deployment_digest (or run_identity_digest)   -> REFUSED

  3 unknown schema (v3 / empty / None)                      -> REFUSED
  4 V2 with a malformed digest (short, uppercase, garbage)  -> REFUSED
  5 V2 record made under D1, verified under D2              -> REFUSED

26. RESIDUAL RISKS
  a) DURABLE ORDERING IS NOT SOLVED. The store is torn-write-safe and mutually
     excluded, but the ordering of the AnchorRecord write against the ANCHORED
     mark under a crash — the write-through watermark and its recovery — is
     Stage 4. A crash between the two leaves a written anchor and an
     un-marked run; that window is declared, not simulated away.
  b) ACLs ARE NOT IMPLEMENTED. `Worker WRITE = denied` on the trusted store is
     assumed by the model and must be established by Stage 6/8 provisioning.
     Until then the separation is architectural, not OS-enforced.
  c) THE FILE LOCK IS ADVISORY and process-cooperative. It prevents two trusted
     writers from dropping each other's transition; it does not stop a
     principal with write access from editing the file directly — that is (b).
  d) `deployment_digest` IS BINDING, NOT PROVENANCE (section 7). A deployment
     can be exactly identified and still not be proven to correspond to the
     claimed source commit.
  e) THE GATE IS A PRIMITIVE, NOT A CALLER. Nothing in production calls
     authorize_publication yet; publish_anchor does not consult it. Stage 6
     owns that wiring, and until it exists the gate protects nothing by itself.
  f) ANCHOR ORDER-OF-OPERATIONS IS THE CALLER'S. publish_anchor writes the
     record and mark_anchored records it; nothing forces a caller to do both,
     or to do them in that order. Stage 6 must, and Stage 4 must make it
     crash-safe.
  g) EPOCH COMES FROM THE CALLER'S TRUSTED CONTEXT. Stage 3 compares the epoch
     it was given against the one recorded; it does not itself read
     ClaimStore. Wiring the two together is Stage 6.
  h) V1 RECORDS REMAIN VERIFIABLE under their historical contract by design. An
     operator who never passes an expected deployment digest gets the old,
     unbound guarantee. The binding is opt-in at the call site until Stage 6
     makes it mandatory in the production path.
  i) THE TRUST PLANE IS NOW 2295 LOC. Every line of it is code whose compromise
     would defeat F-17. It grew for reasons stated in 17-18, and the publisher
     will inherit run_identity at Stage 6.

27. DECISIONS REQUIRING INDEPENDENT REVIEW
  1. PublicationState as a NEW primitive rather than reusing RunState — and the
     reason given (the store's writability, not the vocabulary).
  2. RunIdentity extended IN PLACE, including the newly REQUIRED tree_identity,
     which changes the existing constructor and migrates the Stage-1 tests.
  3. publish_anchor now CROSS-CHECKS the bundle's content digest instead of
     adopting it — a behaviour change to an already-reviewed function.
  4. anchor v2 carrying exactly deployment_digest + run_identity_digest, and
     NOT owner_worker_sid or epoch as separate fields.
  5. V1 kept readable/verifiable under its historical contract, with binding
     opt-in at the call site (residual risk h).
  6. AnchorNotDeploymentBound as a distinct type, introduced because a mutant
     survived (section 16).
  7. kernel.atomic_io and kernel.file_lock entering the TCB to avoid a second
     implementation of two existing primitives (+148 LOC).
  8. create() being idempotent for an identical identity rather than refusing
     every second create.
  9. Identity checks ordered BEFORE state checks in the gate, so a mismatched
     request never receives ALREADY_ANCHORED.
 10. run_id restricted to a storable-name shape by the trusted store.
