4-5. CLASSIFIER ARCHITECTURE AND THE THREE CLASSES
--------------------------------------------------------------------------------------
`gnosis.kernel.git_surface` (KERNEL, pure, stdlib only) turns a `.git` path into
exactly one class:

    KNOWN_TRUST_SENSITIVE          a write can change what Git EXECUTES or how it
                                   RESOLVES, in a way an in-interval undo hides
                                   from the endpoints -> judged (MACHINERY_MUTATED)
    KNOWN_CONTENT_OR_BOOKKEEPING   a write cannot change the trusted identity or
                                   resolution, property stated -> counted
    UNKNOWN                        no rule qualifies it -> MACHINERY_UNQUALIFIED,
                                   fail closed. The only catch-all.

It is imported by the kernel capture to judge write events; the trust plane never
imports it (it reads the recorded verdict), so the publisher closure is unchanged.


6. THE SEMANTIC MATRIX (26 rules + UNKNOWN catch-all)
--------------------------------------------------------------------------------------
    ts.config                      TS  config selects filters, hooksPath, alternates, worktree and extensions — it can redirect resolution and execution
    ts.config-worktree             TS  per-worktree config (extensions.worktreeConfig) sets executable keys like core.fsmonitor
    ts.head                        TS  HEAD is the symbolic ref that defines the checked-out commit; a write changes what every `HEAD`-relative read resolves to
    ts.packed-refs                 TS  the packed form of the ref backend; a write moves what refs resolve to (the packed twin of the loose refs/ rules)
    ts.shallow                     TS  grafts the history boundary; changes ancestry resolution
    ts.commondir                   TS  redirects the common dir — the root of ref/object resolution
    ts.info-grafts                 TS  fabricates commit parentage; changes ancestry resolution
    ts.info-exclude                TS  steers what Git enumerates as ignored/untracked, which shapes the covered-input set and the content fingerprint's untracked hashes
    ts.info-attributes             TS  drives clean/smudge filters and diff behaviour, so it can change what `git diff HEAD` reports for the same bytes
    ts.objects-info-alternates     TS  redirects object lookup to an external store
    ts.objects-info-http-alternates TS  redirects object lookup to an external (http) store
    ts.refs-replace                TS  replace refs substitute one object for another during resolution with the original bytes intact (BLOCKER A)
    ts.refs-heads                  TS  a branch ref is what HEAD resolves to; an in-interval write is the loose form of the packed-refs risk
    ts.refs-tags                   TS  a tag resolves to an object a check may read via `git rev-parse`
    ts.refs-remotes                TS  a remote-tracking ref resolves to an object a check may read
    ts.hook                        TS  a non-sample hook is code Git executes on the next operation
    bk.index                       BK  the staging/stat-cache index; the trusted identity is working-tree vs HEAD (`git diff HEAD`, index-independent) plus endpoint-captured `git status`, so an index write cannot alter identity without moving an endpoint the capture already binds
    bk.index-lock                  BK  the transient lock Git writes and removes around an index update
    bk.sharedindex                 BK  the split-index backing file; same property as index — staging state, captured at the endpoints via `git status`
    bk.loose-object                BK  a content-addressed loose object: its name is the hash of its bytes, so it cannot be made to name different content; F-14 byte-binds tracked content and the redirect rules cover substitution
    bk.pack                        BK  content-addressed pack data; same property as a loose object
    bk.reflog-head                 BK  the HEAD reflog: an append-only record of ref movement, never consulted when resolving a ref to an object
    bk.reflog-refs                 BK  a ref's reflog; append-only movement history, not consulted in ref->object resolution
    bk.commit-editmsg              BK  the last commit message buffer; scratch, never consulted by resolution or by the trusted read
    bk.description                 BK  the human repo description (gitweb only); never consulted
    bk.hook-sample                 BK  an inert example hook Git ships; the `.sample` suffix means it is never executed
    (no rule matches)              UK  UNKNOWN -> MACHINERY_UNQUALIFIED, fail closed

39. RESIDUAL RISKS

    R1  8.3 SHORT NAMES. A short name the observer reports instead of the long
        name (CONFIG~1) will not match an exact rule and falls to UNKNOWN — still
        fail closed, but misclassified as unqualified rather than as the specific
        surface. There is no relative-path long-name canonicaliser (the OS-answer
        canonicalisers need an open handle); recorded, not resolved.
    R2  VERSION STRICTNESS. A git upgrade beyond 2.55.x fails captures closed
        until re-qualified. This is the intended reading of the mandate, but it
        means a routine git update pauses evidence capture until Stage 8/ops
        re-qualify the new version.
    R3  BOOKKEEPING BREADTH vs A REPO-MUTATING CHECK. refs/heads|tags|remotes are
        trust-sensitive, so a check that legitimately commits inside a captured
        interval fails closed (MACHINERY_MUTATED). That is correct for evidence
        capture (the tree must be fixed) but is a behaviour change from Stage 6.
    R4  sharedindex qualified by analogy to index and exercised with core.
        splitIndex on; a future split-index internal format change would need
        re-qualification (it would only ever fail MORE closed).
    R5  The trust gate keys on the boundary verdict STRING in SUMMARY.json; a
        bundle whose manifest and SUMMARY were both forged by a party who can
        write the evidence root could carry a CLEAN verdict. That is the same
        signature-vs-tamper-evidence limit ADR-0027 already declared, and the
        evidence root is ACL-protected (Stage 8 provisions the production ACL).
