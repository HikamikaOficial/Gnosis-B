1. FINAL STAGE 6 ARCHITECTURE
--------------------------------------------------------------------------------------
One executable security path, composed from the independently qualified parts:

    Trusted Director
      -> observe deployment            trust.deployment      (V2: runtime as a TREE)
      -> seal LaunchSpec               trust.launch_spec     (Stage 5, frozen)
      -> launch dedicated Worker       trust.worker_launcher (Stage 5, frozen)
      -> observe the ACTUAL token SID  LaunchedWorkerIdentity.observed_sid
      -> freeze RunIdentity            trust.orchestration.create_trusted_run
      -> Worker runs
      -> trusted completion gate       trust.orchestration.authorize_publishable
      -> NOT_PUBLISHABLE -> PUBLISHABLE
    Worker
      -> "PUBLISH <run_id>"            the entire request surface
    Restricted Service-SID Publisher
      -> load trusted RunIdentity      trust.run_identity
      -> authorize                     authorize_publication (Stage 3)
      -> verify the bundle             trust.bundle_verify   (minimal)
      -> durable publish               trust.publication     (Stage 4)
      -> Anchor v2 committed           trust.anchor

The Worker never receives Publisher authority and cannot manufacture it: the
verbs that would grant it do not exist in the grammar, and the code that could
grant it is not in the service's import closure.


2. TRUSTED ORCHESTRATION PATH
--------------------------------------------------------------------------------------
`gnosis.trust.orchestration` is the whole Director-side seam - deliberately
narrow. The engine keeps its scheduling and retries; only the decisions whose
corruption would let an unauthorized run be anchored moved into the trust plane.

THE ORDER IS ENFORCED BY TYPES. `create_trusted_run` requires a
`LaunchedWorkerIdentity`, which is only ever constructed after
`verify_worker_token` accepted the child's token. No code path invents an
owner SID in advance because none produces that argument in advance. `RunPlan`
has no field for owner SID, deployment digest or launch digest at all.

13-14. DEPLOYMENT DIGEST AND THE RUNTIME MANIFEST
--------------------------------------------------------------------------------------
THE BLOCKING DEBT, CLOSED. A V1 deployment identity measured the interpreter as
ONE FILE. `observe_runtime_tree` now measures the runtime ROOT closed-world:
every file, real bytes read through the handle whose resolved path was taken,
deterministic code-point ordering, nothing excluded, and any artifact resolving
outside the root REFUSED rather than followed.

The runtime root is DECLARED (`DesiredDeploymentConfig.runtime_root`), never
inferred from `runtime_executable.parent`, and `observe_deployment` refuses an
executable that does not resolve inside it - otherwise the two halves of the
binding would describe different installations while reading like a binding.

Covered by `deployment_digest` V2: the trust package (which now includes the
publisher service code, the bundle verifier, the pipe server, the service host,
the launch/bootstrap artifacts and the environment policy, because
`observe_trust_package` excludes nothing under the trust root), the runtime
executable's bytes, AND the runtime tree.

24. DEPLOYMENT MISMATCH — AND WHAT KIND OF GUARANTEE IT IS
--------------------------------------------------------------------------------------
Stated precisely, as required: the guarantee is BOTH, at different granularities.

    PREVENTION BY TRUSTED ACL   the Worker cannot alter the trust package, the
                                runtime, the service configuration or the trust
                                state; all seven write attempts were DENIED
                                OS-real.
    DETECTION AT SERVICE START  the publisher holds `expected_deployment_digest`
                                from its provisioned configuration and refuses a
                                run whose identity names a different deployment.

It is NOT re-observation per request: the 1052-line deployment observer is
deliberately absent from the publisher's closure, so a drift introduced by an
ADMIN between service start and a request would not be detected until restart.
Under T2 that is out of scope; under T4 it is already out of scope. Recorded
rather than claimed away.

41. RESIDUAL RISKS
--------------------------------------------------------------------------------------
    R1  THE RUN IDENTITY IS CREATED JUST AFTER THE WORKER STARTS, not strictly
        before its first instruction: Stage 5's launcher resumes the child
        inside `launch()`, and restructuring that would reopen a frozen
        interface. The window is closed by CONSEQUENCE - a publish request for
        a run with no identity is `unknown-run`, and one before the gate is
        refused - not by sequencing. Stated, not hidden.
    R2  THE PUBLISHER'S RUN-SCOPED EXPECTATIONS COME FROM THE TRUSTED STORE.
        Only the owner SID and the deployment digest are INDEPENDENT (they come
        from provisioning); repository, head, tree, epoch and launch digest are
        read from the record the request selects. That is inherent to a service
        whose only independent knowledge is its own configuration, and it is
        sound because the Worker cannot write the store - but it is not the
        same guarantee as an independent second source, and it is not claimed
        to be.
    R3  DEPLOYMENT DRIFT is answered by PREVENTION plus DETECTION AT SERVICE
        START, not by re-observation per request. See section 24.
    R4  PRODUCTION PROVISIONING IS STILL STAGE 8: real ACLs, the real service
        account, `python._pth` hardening, and the real trust root.
    R5  Everything Stage 5 already carried, plus: the pipe DACL is only as good
        as the SIDs provisioning puts in it.
